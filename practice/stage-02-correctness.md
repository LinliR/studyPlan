## 新增模型与业务规则

- 库存每个 SKU 维护 onHand（在库）、reserved（已预留），available=onHand-reserved，均非负。预留时 reserved 增加；取消释放时 reserved 减少；确认支付后将预留提交为售出，onHand 与 reserved 同量减少。
- 订单从 CREATED 经库存预留进入 PENDING_PAYMENT；库存不足则保留 CREATED 并返回明确失败，可补货后重试。预留的失败不能留下部分 SKU 占用。第一版不做分仓和部分预留。
- PENDING_PAYMENT → PAID 或 CANCELLED；待支付到期走取消。PAID → REFUND_PENDING → REFUNDED。阶段 2 只做整单退款，履约仅做售出标记，不涉及物流。
- 正常退款成功后库存回补一次；晚到支付发生在订单已 CANCELLED 时，不再销售或重复扣库存，保留取消状态并创建独立退款任务，退款结果记录在支付侧。这类异常收款与退款进入资金对账台账，不确认正常成交，也不回补已经释放的库存。
- 每个订单最多一次有效支付确认。模拟渠道可重复发送通知，流水号唯一；金额与订单不一致应拒绝并留下对账记录。未知流水/订单进入待核查，不伪造匹配。
- 库存预留按订单唯一；支付按渠道流水唯一，退款按退款业务号唯一。唯一约束与状态条件更新共同保证幂等，不能只在内存中缓存请求 ID。
- 此阶段各模块仍在同一练习数据库，采用本地事务保护订单和库存；模拟支付渠道用独立的可查询记录表示外部事实，不能假设本地回滚能撤销渠道扣款。

## 验收矩阵

| 场景 | 预期 |
|---|---|
| 正常预留 1 件并支付 | reserved 先 +1，再 -1；onHand 在支付时 -1；订单 PAID |
| 库存为 0，或多 SKU 中一种不足 | 不成功预留；所有 SKU 保持原值；订单可重试 |
| 同订单并发预留/取消 | 每次状态动作最多生效一次；不释放未拥有的数量 |
| 同支付通知重放 10 次 | 只有一次支付确认和一次库存提交 |
| 取消先提交，随后支付成功通知到达 | 订单仍 CANCELLED，退款任务唯一；不重复释放库存 |
| 支付先提交，随后取消到达 | 不执行待支付取消；请求应改走退款流程 |
| 正常退款通知重放 | 累计退款不超实付；整单退款与库存回补各一次 |
| 退款渠道已成功但本地未收到结果 | 通过业务号查询/对账后收敛，不能直接认为未退并无限新建退款 |
| 线程池满、连接池满、慢下游 | 拒绝/超时行为有定义、无无限排队；资源最终释放 |

逐项核对数据库状态及业务总量，不能只看 HTTP 返回。并发正确性与压力容量分开实验，避免混淆失败原因。

## 性能记录要求

先分别测试小数据与放大数据，再增加并发到观察到饱和趋势为止；负载上限以练习机器可承受范围为准。记录 P50/P95/P99、吞吐、错误率、CPU、内存、GC、数据库连接与队列。比较相同预热、样本量和持续时间，报告波动，不把教学数据外推为生产承诺。
