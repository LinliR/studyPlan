# 阶段 5：迁移到真实工作

[实践首页](README.md) · [上一阶段](stage-04-architecture.md) · [个人进度](../PROGRESS.md)

## 目标与前置

入口：已经能完成复杂模块与架构决策练习。选择一个有业务价值、范围可控、能测量反馈的实际问题，把方法用于团队交付。没有真实项目机会时继续做模拟案例，但状态记录为“模拟完成，待真实验证”。

候选问题：慢接口、频繁超时、手工发布风险、模块耦合导致改动困难、权限遗漏、昂贵报表或消息积压。优先选择能取得基线和结果的数据；不要为证明架构能力扩大改造范围。

## 任务与交付

| 任务 | 行动 | 证据与验收 |
|---|---|---|
| S5-01 定义问题 | 明确受影响用户、业务损失、约束、责任人和不做什么 | 脱敏的问题陈述；同事认可问题确实存在 |
| S5-02 建立基线 | 记录指标口径、数据窗口、典型案例和环境 | 原始证据可追溯；区别相关性与因果 |
| S5-03 方案评审 | 至少比较小修、结构调整两类方案，列风险、成本与验证方法 | 评审意见和调整记录；不是只有最终结论 |
| S5-04 小步实施 | 任务拆分、代码评审、发布检查点、观察和回退 | 依团队流程执行；可由其他人复核的变更与测试 |
| S5-05 结果评估 | 同口径比较前后，注明业务量与流量结构变化 | 成功和退化均如实记录；没有收益也总结原因 |
| S5-06 知识传递 | 给同事讲清机制，让其按文档完成一个变式任务 | 反馈与修订，说明哪些决策可以复用、哪些依赖本场景 |

## 验收场景

| 场景 | 应对与检验 |
|---|---|
| 正常 | 指标按预期改善，业务不变量与权限回归仍通过 |
| 边界 | 改造期间流量下降/业务口径变化，重新对齐基线并标注归因限制 |
| 失败 | 效果不明显、出现回归或团队反馈不可维护 |

边界场景需重新对齐基线或明确无法归因；失败场景按预定回退/缩小方案处理，形成复盘，不把“上线”当作成功。

## 高级工程师与架构能力复核

高级工程师证据：独立交付、关键机制解释、故障定位、测试质量、可复现结果和他人可维护的文档。

架构能力证据：从业务约束出发选方案，明确成本与数据边界，组织评审与协作，渐进迁移并观察实际反馈；知道何时撤销自己原来的判断。

产出使用 [ADR](../templates/architecture-decision.md)、[故障复盘](../templates/incident-review.md) 与 [学习证据](../templates/evidence.md)。真实资料需脱敏；无权复制的公司代码和数据不放入个人学习仓库。

## 阶段出口

- [ ] 一次完整的问题→基线→评审→实施→观测→复盘闭环。
- [ ] 至少一位实际协作者能复核结论并提出反馈，反馈已处理或明确保留原因。
- [ ] 有新问题触发的下一轮学习任务，继续更新模块矩阵。
- [ ] 模拟成果与真实工作成果明确区分，不以一次实验推断长期生产可靠性。
