# M04 JVM 与性能诊断

[总纲](../ROADMAP.md) · [阶段 2](../practice/stage-02-correctness.md)

## 学习问题与前置

响应变慢、内存增长或进程退出时，怎样把现象变成可验证的根因？前置：M01 对象与资源、M02 OS、M03 线程基础。目标 L3：以观测排除假设，完成同条件复测。

## 最小实验与项目映射

**实验 A：三种“慢”。** 同一个练习接口分别执行高 CPU 循环、等待同一把锁、等待慢下游。固定输入与并发，记录 CPU、线程状态、JFR 和接口延迟；比较工具证据能否区分三者。

**实验 B：客户导出内存。** 对比一次性加载所有客户与分批读取/输出，逐步增大数据量。注入一个长期保存批次引用的集合；通过堆转储找到保留链，再修复并复测。样本使用虚构数据；转储也视为敏感产物管理。

| 场景 | 验证 |
|---|---|
| 正常 | 稳定输入下资源与延迟基线可复现 |
| 边界 | 小堆、空导出、较大单条记录、容器 CPU 限制 |
| 失败 | 内存耗尽、死循环、死锁、下游超时；比较 CPU 与壁钟时间 |

## 自测与模块验收

1. Full GC 后内存仍很高一定是泄漏吗？通过：讨论正常存活集、堆外内存和泄漏，并给出区分证据。
2. 为什么一次堆转储可能找不到 CPU 问题？通过：说明工具适用范围，选择线程与采样证据。
3. 更换 GC 后 P99 降低但吞吐也下降，如何判断是否值得？通过：关联业务目标与资源成本。
4. 为什么“执行一次循环计时”不足以证明优化？通过：说明预热、测量噪声和编译优化。

至少完成 CPU、等待、内存三类诊断；优化报告依照 [证据模板](../templates/evidence.md)，相同负载重复至少 3 次。现有测量无法区分假设时继续补证据。

## 一手资料与阅读顺序

主入口：[JDK 21 故障排查指南](../resources/REFERENCES.md#jvm)，先读诊断流程与工具，再按问题查内存和性能章节；基准实验查 JMH。字节码/运行时概念回查 Java 21 规范与对应发行版工具文档。

## 选修与边界

HotSpot C++ 实现、收集器算法证明、复杂字节码增强、Native Image 调优为选修。练习可用较小内存触发故障；真实环境诊断需考虑暂停、磁盘与采样成本。
