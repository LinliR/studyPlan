# M07 软件设计与工程质量

[总纲](../ROADMAP.md) · [阶段 1](../practice/stage-01-business.md)

## 学习问题与前置

怎样让需求变化的代价可控，让别人能验证和维护自己的交付？前置：M01 基础；测试数据库边界时配合 M05/M06。目标：实现与排障达到 L3，设计取舍达到 L4。

## 最小实验与项目映射

**实验 A：安全重构。** 先把报价计算、状态判断和数据库操作混在一个应用服务中，补齐金额和失败回滚测试；分步抽出纯计算和仓储接口。比较修改“报价到期规则”前后的影响范围。

**实验 B：测试层级。** 用单元测试验证金额；用真实 MySQL 验证唯一约束与事务；用 HTTP 集成测试验证权限及错误码。故意删掉唯一约束，确认相关测试确实失败。

**实验 C：可复现交付。** 在全新工作目录按说明拉取依赖、初始化库、测试、打包；记录 JDK、构建工具、锁定依赖和制品校验值。自动化尚未建立时先手工验证同样流程，再放入 CI。

| 场景 | 验证 |
|---|---|
| 正常 | 新增报价规则后原有测试仍保护旧行为 |
| 边界 | 日期跨日、空输入、构建无本地缓存、两个提交修改同一处 |
| 失败 | 回归测试失败、数据库不可用、依赖冲突、错误配置导致启动失败 |

## 自测与模块验收

1. 覆盖率很高为什么仍可能漏掉业务错误？通过：举出无有效断言或 mock 遮蔽边界的例子。
2. 何时不应该引入设计模式？通过：根据变化频率和理解成本比较两种实现。
3. 测试失败但只在某台机器发生时怎样定位？通过：检查版本、时区、随机性、并发和外部依赖。
4. 为什么不能把“编译成功”当交付完成？通过：给出包含行为、文档和恢复的完成定义。

交付一次有测试保护的重构和一次由 CI 阻止的错误变更；评审记录至少包含一个根据反馈调整的决定。
