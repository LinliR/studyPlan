# M10 部署、可观测性与可靠性

[总纲](../ROADMAP.md) · [阶段 3](../practice/stage-03-resilience.md)

## 学习问题与前置

如何知道用户正在受影响，如何恢复，怎样判断“足够可靠”？前置：M02 Linux/网络、M06 应用，M07 构建。阶段 1 先建立部署与日志基线，阶段 3 深入；目标 L3/L4。

## 最小实验与项目映射

**实验 A：面向用户的监控。** 为“报价转订单”定义请求成功率、P95/P99 和吞吐，再为事件链定义最老未投递事件年龄、消费失败与积压。用固定请求集制造异常，核对业务错误与系统错误统计是否混淆。

**实验 B：发布与恢复。** 先记录旧版本健康基线，发布一个错误配置版本，验证探针、告警和回滚。再在独立实例从备份恢复数据库，用订单数、金额合计和抽样行核对，记录实际 RTO/RPO。

| 场景 | 验证 |
|---|---|
| 正常 | 新实例就绪后接流量，追踪关联 API 与异步处理 |
| 边界 | 资源达到限制、低流量窗口、队列增长、部分实例尚未就绪 |
| 失败 | 配置错误、下游断连、容器重启、磁盘不足、恢复文件不可用 |

## 自测与模块验收

1. CPU 告警和用户成功率告警分别回答什么问题？通过：区分资源原因与用户影响。
2. 99.9% SLO 如果没有时间窗口有什么问题？通过：补上分母、窗口、测量点和错误预算口径。
3. 加副本为什么可能把数据库压垮？通过：估算连接与在途量的总和。
4. 回滚代码为什么不能保证数据回滚？通过：说明兼容迁移和不可逆写入处理。

交付观测面板或等价查询、告警说明、发布/恢复记录和一次复盘。小样本演练只验证机制，不据此宣称达成长期可用性。

## 选修与边界

多集群、云平台认证、Service Mesh、全自动容量管理为选修；Kubernetes 的机制理解与最小演练必修，不要求一开始管理生产集群。云账号与付费资源不作为课程前置。
