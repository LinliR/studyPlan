# M08 缓存、消息与搜索

[总纲](../ROADMAP.md) · [阶段 3](../practice/stage-03-resilience.md)

## 学习问题与前置

缓存、异步消息和搜索分别改变了哪种成本，又引入了哪种不一致？前置：M05 事务/索引、M06 接口；可靠投递与 M09 联动。Redis 与 RabbitMQ 为主要实现，目标 L3；搜索基础目标 L2。

## 最小实验与项目映射

**实验 A：客户摘要缓存。** 定义数据库为事实来源，缓存只保存可重建摘要。并发“读旧值、更新数据库、删除缓存、旧值回填”，画出陈旧值形成的时序，再选择 TTL/版本校验等策略并解释残余窗口。

**实验 B：成交事件。** 消费者更新客户统计并登记事件 ID，在数据库提交后、确认消息前故意退出；重启后观察重投，验证成交额没有重复增加。另一轮在提交前退出，验证事务回滚后消息仍可处理。

**实验 C：客户搜索。** 至少验证新客户、重命名、删除/停用、中文分词和跨负责人访问。搜索结果只作为检索入口，详情权限在服务端重新校验。

| 场景 | 验证 |
|---|---|
| 正常 | 命中缓存；成交更新统计；新客户可检索 |
| 边界 | 空值、热键、消息乱序、同 ID 重放、索引尚未刷新 |
| 失败 | 缓存断连、确认丢失、消费者重启、永久格式错误、搜索索引丢失 |

## 自测与模块验收

1. Redis 可用是否意味着缓存数据一定完整？通过：区分故障切换、淘汰、持久化与业务事实来源。
2. 发布确认成功是否代表 CRM 统计已完成？通过：解释确认所属层次与业务状态查询方式。
3. 为什么“先写去重表，再单独更新统计”仍可能漏处理？通过：给出中间崩溃时序，并用同事务修复。
4. 搜索返回旧名称时如何判断是故障还是允许延迟？通过：关联同步机制与可见性目标。

验收必须提交组件失败矩阵、重复消费证据和一次重建/重放记录；Redis/MQ 的持久化与队列配置注明版本和具体值。

## 选修与边界

Kafka、Redis Cluster、Lua 脚本深入、CDC、搜索集群调优为选修。Kafka 对照重点是日志/分区/消费位点语义；不为凑技术栈同时引入两种 MQ。
